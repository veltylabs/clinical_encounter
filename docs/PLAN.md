# clinical_encounter: supply use of an attention (domain and operations)

## Why

A clinic attention consumes supplies (gloves, syringes…). Each **service** already has a **recipe**
of supplies in `service_catalog`; `supply_manager` already knows how to take stock out of the
location that supplies a **room** (box); `room_layout` already knows in which room a professional
has a shift at a given instant. This plan makes the attention use all three — without importing
any of those modules: it declares three narrow interfaces and the application passes the real
modules (ecosystem rule: no module imports another module).

Decided by the owner (do not change):

| Rule | Behaviour |
|---|---|
| Tenant | `medical_history` and the new `encounter_supply` carry `tenant_id`; every query and operation filters by it |
| Recipe | When a visit is created with a `service_id`, the service's recipe becomes its supply lines (`from_recipe = true`, status `planned`) |
| Adjust | Before completing, a professional (permission `encounter_supply_use`) changes quantities, adds or deletes lines |
| Billable | Each line has `billable`, **false by default** |
| Deduction | Stock is taken **once**, when the visit is **completed**. A cancelled or never-completed visit never touches stock |
| Room | The room is the one where the doctor has a shift at `attention_at` (`RoomOfOccupant`) |
| Failure | If a line cannot be deducted (no shift, the room has no supply location, not enough stock, expired…) the visit **is completed anyway**; that line becomes `pending_deduction` with the reason, and **one** alert is raised to the Supplies area, which retries the line from its own screen |

Out of scope (later plans): the screens (the list before completing, the Supplies pending screen),
the demo wiring of `room_layout`/`supply_manager`, the `browser`/`!browser` tag migration.

## Stage 3 — tenant everywhere (`visit.go`, `patients.go`)

- `CreateVisit(args)`: `args.TenantId == ""` → `ErrTenantRequired` (checked before `ErrMissingArgs`);
  copies `TenantId` and `ServiceId` into the record. The idempotency lookup becomes
  `m.GetVisit(args.TenantId, args.Id)`.
- `GetVisit(tenantId, id string)`, `ListVisitsByPatient(tenantId, patientId string)`,
  `ListRecentPatients(tenantId string, limit int)`: `tenantId == ""` → `ErrTenantRequired`; every
  query adds `.Where(MedicalHistory_.TenantId).Eq(tenantId)`.
- After the record is created **and** `m.supplyOn` **and** `record.ServiceId != ""`: call
  `m.recipes.ServiceRecipe(tenant, serviceId)`; for each index `i` create an `EncounterSupply{Id: m.ids.NewID(), TenantId, EncounterId: record.Id, ItemId: itemIds[i], Quantity: quantities[i], Billable: false, FromRecipe: true, Status: SupplyPlanned, UpdatedAt: time.NowNano()}`.
  An error from `ServiceRecipe` is returned (the visit stays created; a retry of `CreateVisit` with
  the same id returns the existing visit and does **not** copy the recipe again: only copy when the
  visit did not exist before this call).

| Call | Result |
|---|---|
| `CreateVisit{TenantId:"t", ServiceId:"s1", …}`, recipe of s1 = `[i1 ×2, i2 ×1]` | visit + 2 lines `planned`, `from_recipe`, `billable=false` |
| same, recipe empty | visit, 0 lines |
| `ServiceId == ""` | visit, 0 lines, `ServiceRecipe` not called |
| supply use off | visit, 0 lines |
| `TenantId == ""` | `ErrTenantRequired` |
| same `Id` again | existing visit, still 2 lines |

## Stage 4 — supply lines (`supply.go`, new)

All return `ErrSupplyUseOff` when `!m.supplyOn` and `ErrTenantRequired` when tenant is `""`.

| Method | Behaviour |
|---|---|
| `ListSupplyUse(tenantId, encounterId string) ([]*EncounterSupply, error)` | lines of the visit, tenant-filtered |
| `UpsertSupplyUse(args UpsertSupplyUseArgs) (*EncounterSupply, error)` | `Quantity <= 0` → `ErrQuantity`; visit not found (same tenant) → `ErrNotFound`; visit `Completed`/`Cancelled` → `ErrVisitClosed`. `Id == ""` → new line `{Id: ids.NewID(), FromRecipe: false, Status: SupplyPlanned}`. `Id != ""` → line not found → `ErrSupplyNotFound`; line `deducted` → `ErrLineDeducted`; else update `ItemId`, `Quantity`, `Billable`, `UpdatedAt` |
| `DeleteSupplyUse(tenantId, id string) error` | not found → `ErrSupplyNotFound`; visit closed → `ErrVisitClosed`; else delete |
| `ListPendingSupply(tenantId string) ([]*EncounterSupply, error)` | every line of the tenant with status `pending_deduction` |
| `RetrySupplyUse(tenantId, id, by string) (*EncounterSupply, error)` | line not `pending_deduction` → `ErrLineNotPending`; else run `deductLine` (Stage 5) again with the visit's doctor and `attention_at`; returns the line with its new status |

Every update or delete filters by `Id` **and** `TenantId` (`orm.Eq(EncounterSupply_.Id, …), orm.Eq(EncounterSupply_.TenantId, …)`, as `service_catalog/recipe.go` does).

## Stage 5 — completing the visit (`complete.go`, new)

```go
// CompleteVisit marks the visit completed and takes its planned supply lines out of stock, once.
// A line that cannot be taken stays pending_deduction with the reason; the visit is completed anyway.
func (m *Module) CompleteVisit(tenantId, id, by string) (*MedicalHistory, []*EncounterSupply, error)
```

1. `tenantId == ""` → `ErrTenantRequired`; `GetVisit` errors are returned as they are.
2. Status `completed` or `cancelled` → `ErrVisitClosed`.
3. Update the visit: `Status = StatusCompleted`, `FinishedAt = time.NowNano()`, `UpdatedAt = time.NowNano()`
   (filter by id and tenant). Publish `TopicVisitCompleted` with the record when `m.pub != nil`.
4. If `!m.supplyOn`: return the visit and `nil`.
5. For every line of the visit with status `planned`, call `m.deductLine(visit, line, by)`:

```go
func (m *Module) deductLine(v *MedicalHistory, l *EncounterSupply, by string) error {
	roomID, found, err := m.rooms.RoomOfOccupant(v.TenantId, v.DoctorId, v.AttentionAt)
	switch {
	case err != nil:
		l.Status, l.Failure = SupplyPendingDeduction, err.Error()
	case !found:
		l.Status, l.Failure = SupplyPendingDeduction, msgNoShift
	default:
		cost, useErr := m.supplies.UseInRoom(v.TenantId, roomID, l.ItemId, l.Quantity, SupplyDocType, v.Id, by)
		l.RoomId = roomID
		if useErr != nil && cost == 0 {
			l.Status, l.Failure = SupplyPendingDeduction, useErr.Error()
		} else {
			l.Status, l.Cost, l.Failure, l.DeductedAt = SupplyDeducted, cost, "", time.NowNano()
		}
	}
	l.UpdatedAt = time.NowNano()
	return m.db.Update(l, orm.Eq(EncounterSupply_.Id, l.Id), orm.Eq(EncounterSupply_.TenantId, l.TenantId))
}
```

   with `const msgNoShift = "the professional has no shift in a room at the attention time"`.
   A `cost > 0` with an error means the stock was taken (only supply_manager's cost fact failed): the
   line is `deducted`; never retry it.
6. If at least one line ended `pending_deduction` and `m.pub != nil`: raise **one** alert:

```go
notify.Raise(m.pub, notify.Alert{
	Code:    AlertSupplyPending,
	Scope:   m.suppliesArea,
	Level:   msgtype.Warning,
	Subject: alertSubject, // "Supplies pending deduction"
	Body:    alertBody,    // "An attention was completed with supplies that could not be taken from stock. Open Supplies to retry them."
	Source:  notify.Ref{Type: SupplyDocType, ID: v.Id},
})
```
   (`alertSubject`/`alertBody` are named constants in `alerts.go`.) A `Raise` error is returned
   **after** all lines were processed (the visit stays completed).
7. Return the visit and all its lines.

| Setup (fakes) | Call | Expected |
|---|---|---|
| 2 planned lines, room `r1`, stock ok (cost 100, 50) | `CompleteVisit` | visit `completed`; both `deducted`, `room_id=r1`, costs 100/50; `UseInRoom` called twice with docType `medical_history`, docId = visit id; no alert |
| no shift (`found=false`) | same | visit `completed`; both `pending_deduction`, failure `msgNoShift`; `UseInRoom` not called; **one** alert, Scope = SuppliesArea, Source = visit |
| `UseInRoom` returns `(0, errors "supply: not enough stock")` for line 2 | same | line 1 `deducted`, line 2 `pending_deduction` with that text; one alert |
| `UseInRoom` returns `(70, err)` | same | line `deducted`, cost 70 |
| visit already `completed` | same | `ErrVisitClosed`, `UseInRoom` not called |
| a `deducted` line exists from before | — | impossible by step 2; only `planned` lines are processed |
| supply use off | same | visit `completed`, lines `nil` |
| then `RetrySupplyUse` on the pending line with stock fixed | — | line `deducted`; `UseInRoom` called once more |
